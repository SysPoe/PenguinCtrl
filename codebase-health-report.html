Capable code.
Too much of it lives together.

PenguinCtrl is not a 24,000-line toy that has somehow become bloated. It is a compact but feature-dense native show-control system. The raw size is defensible; the concentration is not. Two files are unequivocal size “hell files”, 13 more are in the oversized red zone, and 15 files contain 61.2% of all production code.

6.3
Overall: promising engineering, prototype-level maintainability

The package boundaries, operational safeguards, tests, and CI are better than the file layout suggests. The biggest risks are enormous orchestration functions, low UI/media coverage, rapid single-maintainer churn, and missing project documentation. This needs a controlled decomposition, not a rewrite.

01 · Size

Is 24k LOC too high?

Not automatically. The more useful question is how much of that code represents necessary product capability, how much is test protection, and how concentrated the remaining code is.

83.6% production 16.4% tests
20,451 production code lines 4,004 test code lines 26,986 physical Go lines including 327 comment-only and 2,204 blank lines

The total is plausible

Gio requires explicit layout and interaction code. PenguinCtrl also owns FFmpeg process control, native audio mixing, video output windows, archive integrity, remote protocols, timecode, redundancy, health monitoring, crash recovery, and release packaging. Those are real responsibilities.

The distribution is unhealthy

The top 10 files hold 48.4% of production code. The top 21 hold 72.9%. A change to everyday playback or UI behaviour therefore repeatedly enters the same few high-churn files.

Do not optimize the wrong number

Deleting tests would make cloc look better and the product worse. Track production LOC, test LOC, file concentration, long-function count, and coverage as separate indicators.

Recommended size target: reduce production code to roughly 17,500–18,500 lines through consolidation and declarative UI/rule definitions. That is a credible 10–15% reduction. Keep or grow the 4,004 lines of tests; total repository LOC may remain near 24k even while maintainability improves sharply.

03 · Structure

How far can it be broken down?

Substantially—but mostly within existing packages. The goal is 150–400 code lines per cohesive file and functions under 50 lines, not a new package for every noun.

01 · ROOT

App shell

  • bootstrap.go
  • window_loop.go
  • document_controller.go
  • preflight_controller.go
  • shortcuts.go
02 · PLAYBACK

Runtime kernel

  • command scheduler
  • cue executor
  • link/timecode scheduler
  • media/output controller
  • instance state + safety gates
03 · MEDIA

Device runtime

  • decoder pool
  • FFmpeg session
  • probe service
  • audio endpoint mixer
  • output-window controller
04 · UI / SHOW

Operator surfaces

  • row projection + renderer
  • timeline state/input/paint
  • settings field schemas
  • typed warning rules
  • focused dialogs/panels

Expected structural result

The 15 oversized files can become roughly 40–50 cohesive files, mostly inside the same packages. The total tracked Go file count would rise from 162 to about 185–200, but the new files should average 200–350 code lines—not five lines.

Package boundary adjustment

The root package currently imports nearly every internal subsystem, which is normal for a composition root; the problem is that one App.run method also coordinates them. Add an application-controller layer, preserve dependency direction, and keep playback independent of concrete media implementations.

Important distinction: splitting a file improves navigation and ownership but does not make code more concise. Pair mechanical splits with explicit state machines, declarative UI schemas, shared validation constructors, and deletion of legacy APIs; otherwise the project simply has more files containing the same complexity.
04 · Simplification

How much more concise can it get?

A safe first programme can remove approximately 2,000–3,000 production lines. Pushing much further would likely trade visible lines for hidden framework complexity or regressions in show-critical behaviour.

OpportunityCredible savingMechanismRisk
Declarative Gio forms and repeated sections700–1,100Field descriptors, shared labelled rows, reusable dynamic-list editors, typed binding/validationMedium
Application/document lifecycle350–600One document controller for open/save/dirty/recovery/progress; one service lifecycle registryMedium
Warning/problem rules200–350Typed rule registry and shared problem constructors instead of string-to-code/field mappingLow
Playback/media state transitions250–450Explicit state/event transitions shared by command, instance, player, and output lifecyclesHigh
Cue editor variant plumbing250–400Common cue-field schemas plus custom sub-editors only for genuinely unique behaviourMedium
Legacy/trivial APIs and wrappers50–120Remove unused GetCue/Cues shapes, alias-only files, and the ternary helper where call sites are clearer inlineLow

Best first deletion

The old pointer-shaped manager APIs now return deep copies, so the earlier race risk is fixed. Their signatures remain misleading and appear unused by production call sites. Replace them with value-returning methods, migrate tests, then delete the compatibility alias.

Best leverage

The UI package alone is 5,946 production code lines, plus 732 in ui/input. Repeated form/layout scaffolding is the largest safe concision opportunity and has less runtime risk than compressing playback code.

Do not over-compress

FFmpeg session management, audio failover, output routing, and archive integrity are complex because the problem is complex. Prefer explicit state and strong tests over clever abstractions that save a few lines.

07 · Maintenance

Maintenance health: volatile

The repository is only 16 days old at this snapshot. High churn is understandable, but the current pace and ownership pattern mean structural debt is compounding faster than documentation and review controls can catch it.

Velocity

92 commits on HEAD

78 landed in the last seven days and 61 in the last 24 hours. The project is still in rapid formation, so APIs and file boundaries should not yet be treated as stable.

Bus factor

One contributor on HEAD

Knowledge of event-loop invariants, media lifecycles, archive safety, and operator behaviour is concentrated in one person and mostly in code rather than documents.

Automation

CI is a real strength

Two Windows versions, race testing, vulnerability scanning, evidence capture, signing, packaging, install/upgrade/rollback, and SBOM output are already present.

Highest-churn hotspots

playback/engine.go has 2,572 changed lines in the 90-day history; main.go 2,344; ui/main_page.go 1,933. They are simultaneously the biggest, most complex, and most frequently edited files—the classic risk multiplier.

Other high-churn files: media player/manager/backend, settings, timecode, warnings, and audio.

Documentation and release defects

  • No tracked README, license, architecture guide, contributing guide, changelog, or security policy.
  • The release workflow publishes with --notes-file docs/release-notes.md, but that file and the entire docs/ tree are absent at this snapshot.
  • Naming spans PenguinCtrl, CuSus, the cusus module, and cusus.exe. If intentional, document product/repository/module naming; if not, complete the rename.
Maintenance verdict: day-to-day change is currently viable because the author holds the whole system in working memory. That does not scale. Without file/function limits, architecture notes, bounded integration tests, and review gates, future features will continue to accrete in the same 15 files.

Prevention

Definition of done for the refactor

  • No production file over 700 code lines; only justified domain tables over 500.
  • No function over 100 lines; UI layout/event methods target 50–80 maximum.
  • Top 15 files hold less than 45% of production LOC, down from 61.2%.
  • Overall statement coverage exceeds 45%; UI pure logic exceeds 60%; media non-hardware logic exceeds 55%.
  • Default tests finish under a documented timeout without external hardware.
  • All public maintenance and release workflows are documented from a fresh checkout.

What not to do

  • Do not rewrite the whole application or swap Gio merely to reduce LOC.
  • Do not merge valid platform-tag files to make the file count prettier.
  • Do not delete or compress tests to chase cloc.
  • Do not extract dozens of tiny packages; start with files and internal controllers.
  • Do not change playback semantics while moving code unless a characterization test proves the contract.
