Executive summary

Recommendation: keep cue-list warnings visible and non-modal during programming, add a persistent warning inspector and inline editor guidance, and introduce an invasive prompt only for a small class of trigger-time blockers. Ordinary cautions should never create a popup on every GO.

One icon is not a workflow

The current hover tooltip lists messages, but it cannot be clicked to inspect, navigate, fix, acknowledge, or show warnings hidden inside a collapsed cue group.

2

Playback failures are too quiet

Immediate GO errors are logged or discarded; asynchronous engine errors have no main-window presentation; player startup failures are log-only.

3

Not every “warning” is equal

A disabled cue is an intentional state, while a missing file is a blocker. Treating both as the same amber icon makes the system less trustworthy.

What the product does today

What is already detected

The cue validator covers a useful structural baseline:

  • disabled cues, missing or duplicate internal cue IDs;
  • negative pre/post waits and invalid link modes or explicit cue targets;
  • missing media settings, missing/inaccessible files, negative or reversed clip timing, and negative fades;
  • unsupported timecode actions and problems inside enabled timecode markers;
  • missing remote fields and unknown remote protocol/action values;
  • invalid wait types/targets, media-control requirements, fade curves, and output-control timing.

How the operator sees it

  • An amber warning icon occupies the first cue-list column.
  • Hovering shows a bullet-list tooltip.
  • Saving a cue does not validate, block, summarize, or direct the user to a problem field.
  • There is no show-wide warning count, filter, warning panel, or next-warning navigation.
  • Collapsed groups hide their cue rows without rolling warning state up to the group header.

The critical feedback gap

Space logs an immediate PlaySelected error; the sidebar GO button explicitly discards it. Errors raised after queueing are recorded in the engine and published to output windows, but the main window never reads the engine’s last error. A media player that cannot start logs the failure and removes the instance without recording a cue error. From the operator’s perspective, GO can therefore appear to do nothing.

User impact: the most important warning is not “this cue looks questionable while editing”; it is “the cue you just trusted did not run.” That result must be immediate, visible, attributed to a cue, and retained long enough to review.

Also reconsider “Cue is disabled”: disabled is normally a state, not a fault. Render it as a muted disabled badge. Promote it to an error only when the operator tries to GO it or another cue tries to auto-play it.

Use four user-facing states

Blocker
The cue cannot perform its intended action now.
Red icon and row accent. Prevent trigger, explain why, and provide Edit/Settings/Skip actions. Cannot be dismissed.
Caution
The cue can run, but the result may be partial, surprising, or context-dependent.
Amber icon. Do not show a modal by default. Permit acknowledgement if the choice is deliberate.
Advisory
Data quality or programming guidance with no immediate show risk.
Blue/info treatment in the inspector and editor; no GO interruption.
State
Disabled, not yet preflighted, intentionally indefinite, or waiting for runtime context.
Neutral badge. Never inflate the warning count unless it becomes actionable.

The underlying record should be structured rather than a string: stable code, severity, cue ID, field/tab, short title, consequence, details, suggested action, and whether the result is static, settings-dependent, live-state-dependent, or runtime-only.

Should GO show a more invasive popup?

Sometimes—but only for blockers on a directly triggered cue. A popup for every amber warning would train operators to dismiss warnings and would make time-critical playback less dependable.

Direct GO

  • Revalidate the selected cue against the exact current settings and live state.
  • If clear: trigger immediately.
  • If cautions only: trigger immediately and show a brief non-modal result/banner. Optionally support “GO again to confirm” for a tiny configurable class of high-risk cautions.
  • If blocked: do not enqueue. Show a focused modal/sheet naming cue number and the top reason, with Edit cue, Open settings when relevant, Skip to next, and Cancel. Do not offer “Run anyway” for an impossible action.

Automatic links and timecode

  • Never open an unattended modal in the middle of an automatic chain.
  • Stop only the affected branch, preserve unrelated active media, select/highlight the failed cue, and show a persistent red banner.
  • Record “Triggered by cue 12.5 link” or “Triggered at 00:31.200 in cue 8” so the operator can reconstruct what happened.
  • Give STOP ALL and FADE ALL visual priority over any warning surface.

Press GO

Capture selected cue and current environment as one validation snapshot.

Classify

Clear, caution, or blocker. Do not collapse them into one warning boolean.

Act

Run immediately, run with non-modal feedback, or block with a focused resolution sheet.

Report result

Show Started, No target matched, Failed, or Completed—attributed to the cue.

Warning review and resolution workflow complete

1. Make the cue icon clickable

Hover can remain as a fast preview, but click should open a persistent inspector. Each item should answer:

  • What is wrong?
  • What will happen if I press GO?
  • Where do I fix it?
  • Has the fix been rechecked?

2. Add a show-wide Problems view

A top-bar badge such as 2 blockers · 5 cautions should open a filterable list ordered by cue-list position. Include Blockers/Cautions/Advisories, unresolved/acknowledged, and next/previous controls.

3. Resolve in context

“Fix” should select the cue, open the editor on the relevant tab, scroll to the field, and show an inline message. The editor should have its own problem summary and update it live.

4. Validate at sensible boundaries

Run cheap checks on every edit; recheck on Save, show load, settings change, file change, and before GO. Run media probes asynchronously with visible “Checking…” state and a cache keyed by path plus file modification data.

Definition of a good warning experience

Before the show

The operator can see whether the show has blockers, review all problems quickly, and jump directly to each fix.

During programming

Problems appear beside the field that caused them without preventing incomplete work from being saved when safe.

During playback

GO remains fast. Only impossible actions interrupt; every failure is visible and attributed; emergency controls always remain available.
