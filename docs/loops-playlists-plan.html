PenguinCtrl product plan

Loops, playlists and vamps that remain safe during a live show

A user-facing design and Gio-native implementation plan for repeating one cue, running an ordered set of cues, vamping until the operator releases the sequence, and stopping that automation predictably. The proposal extends the current cue list and playback engine; it does not introduce a browser or server runtime.

Recommendation

Build three clear user features on one internal mechanism.

Add Repeat for a fixed or endless loop, Playlist for an ordered sequence, and Vamp until GO for an intro / repeating middle / outro structure. All three use a cancellable sequence runner in playback; none is simulated by creating circular cue links.

01

Repeat a cue

In the cue editor: Once, a fixed number of plays, or Forever. Optional delay between plays.

02

Run a playlist

A Playlist cue references cues in a chosen order and exposes current item, pass count, Next, Previous, Pause and Stop.

03

Vamp until GO

Play an intro once, repeat a cue or range, then leave at the next safe boundary when GO is pressed.

04

Fail safe

STOP ALL and FADE ALL cancel future playlist starts before stopping or fading active media.

Behaviour from the operator’s side

Simple loop

Loop one cue

  1. Edit a Sound, Video, Image, Wait, Remote or Control cue.
  2. Open the new Repeat tab.
  3. Choose Once, Play through… times, or Loop forever.
  4. Optionally set a delay between plays.
  5. Press GO normally. The row shows Pass 2 / 4 or Pass 2 / ∞.

For media, the next pass starts after natural end. An image with no duration cannot auto-repeat and is flagged before playback.

Multi-cue sequence

Create a playlist

  1. Choose Add Cue → Playlist.
  2. Name it and add existing cues using a searchable picker.
  3. Drag items into order; the same cue may appear more than once.
  4. Choose Sequential or Shuffle and Once / N times / Forever.
  5. Save and press GO. Playlist progress appears in the cue row and sidebar.

Deleting a referenced cue leaves a visible “Missing cue” item and warning rather than silently changing the running order.

Vamps, holds and loop regions

A vamp is not just an infinite loop.

It has a musical or show-safe way out. The operator presses GO while the vamp is running; PenguinCtrl shows EXIT ARMED, finishes the current loop at its configured boundary, and then continues into the outro or next playlist item.

Whole cue

Vamp one cue

A normal cue repeats until GO. By default, GO lets the current pass finish before continuing. This is suitable for complete music beds or repeated waits.

Playlist range

Vamp several items

Mark a first and last playlist item. The intro items run once, the marked range repeats, and the outro items run after GO releases the vamp.

Inside media

Vamp part of a file

Set Loop In and Loop Out on the existing waveform/timeline. The intro plays once, the region loops, and release allows playback past Loop Out into the file’s outro.

Runtime rules

IdleGO creates one run
→
StartingResolve and validate order
→
PlayingRun current item
→
Vamp / holdRepeat or await GO
→
Finish / repeatLink once or next pass

Links are suppressed inside a playlist

Each playlist item runs the referenced cue action, timing and repeat setting, but not its global cue link. Otherwise a child’s “Start Play → Next” can escape the playlist or create two competing sequences. The Playlist cue’s own link fires once, after the whole playlist ends.

One active run per source cue

Pressing GO on a transport-focused vamp releases it; pressing GO on a hold continues it. It never stacks duplicate automation. An explicit Restart cancels and replaces a run. Different playlists may run concurrently.

GO becomes a transport command

Add one Engine.Go() path for the sidebar button and Space shortcut. It first services the focused active vamp/hold; only when none needs GO does it call the selected cue. This avoids different keyboard and button behaviour.

Completion must be explicit

Media completes at natural end; Wait completes when satisfied; Remote and Control complete after dispatch. Images require a duration. A paused or indefinite item holds the playlist rather than guessing.

Errors default to stop

A missing cue, disabled cue, failed media open or failed remote dispatch stops the playlist and leaves a visible error. A later editor option can allow Skip failed item.

Implementation architecture

The current engine already executes cues concurrently, tracks active instances/executions, resolves cue targets and cancels work through runCtx. The missing piece is a first-class run coordinator that knows when an action has completed and owns all work started by that run.

Suggested saved shape 
type CueRepeat struct {
    Mode       RepeatMode // once, count, forever
    TotalPlays int        // used only by count; minimum 2
    DelayMs    int64
}

type PlaylistItem struct {
    ID        PlaylistItemID
    CueID     CueID
    HoldAfter bool // HOLDING until Engine.Go()
}

type VampRegion struct {
    FirstItemID PlaylistItemID
    LastItemID  PlaylistItemID
    ExitMode    VampExitMode // end_of_pass, immediate
    MaxPasses   int          // 0 = unlimited
}

type PlaylistPlay struct {
    Items       []PlaylistItem // stable item ID + referenced cue ID + hold
    Order       PlaylistOrder // sequential, shuffle
    Repeat      CueRepeat
    BetweenMs   int64
    Vamp        *VampRegion // first/last item IDs + exit mode
    OnError     PlaylistErrorPolicy // stop, skip
}

type MediaVamp struct {
    LoopInMs  int64
    LoopOutMs int64
    ExitMode  VampExitMode
}

Use stable playlist item IDs because the same cue may appear more than once and a vamp boundary must identify the exact occurrence. Use “total plays” in the model and UI so stored values have one unambiguous meaning.

Delivery plan

1

Runner foundation

Add models, cloning, warnings, completion reporting, cancellation, repeat-one-cue support and engine tests. No playlist UI yet.

Lowest-risk seam: prove Stop All / Fade All and final-link semantics first.

2

Repeat UI

Add the Repeat tab, row progress (“Pass 2 / 4”), validation and sidebar Stop/Restart behaviour.

This gives immediate useful looping before the larger playlist editor lands.

3

Playlist cue

Add Playlist type, cue picker, reorder/remove controls, sequential playback, progress snapshots and missing-reference warnings.

Ship Sequential + Stop on error first.

4

Vamps and holds

Add playlist vamp ranges, per-item Hold for GO, transport focus, Engine.Go(), EXIT ARMED status and Release Now.

Prove concurrent sequences cannot consume the wrong GO.

5

Media loop regions

Add Loop In/Out handles and clock-aware intro/loop/outro playback, then measure and audibly test boundary gaps.

Do not claim seamless musical looping until the decoder path proves it.

6

Transport polish

Add Previous/Next/Pause, expandable child monitoring, shuffle-without-immediate-repeat, skip-on-error and accessibility/keyboard handling.

Native smoke-test the real Gio window after static tests.

Acceptance tests

  • An old show with no repeat fields behaves byte-for-byte the same at playback.
  • A cue set to “Play through 3 times” starts exactly three times, then fires its own cue link once.
  • A forever loop stops immediately from Stop, STOP ALL, show load, engine close and app shutdown.
  • FADE ALL cannot cause a playlist to advance after the fade completes.
  • A five-item playlist plays in saved order, applies one between-item delay, and reports item/pass progress.
  • Playlist child links never escape or double-trigger the sequence.
  • Remote/control items complete after dispatch; a finite Wait completes when satisfied.
  • Invalid image duration, self-reference, nested cycle and deleted cue reference produce clear warnings.
  • Pressing GO twice on the same active Playlist cue does not create a second runner.
  • GO during a vamp arms one exit, finishes the current pass, runs the outro once and fires the Playlist cue link once.
  • Release Now exits immediately using the configured fade and never starts another vamp pass.
  • A Hold for GO remains stable indefinitely and exactly one GO continues it.
  • Space and the large GO button share the same focused-run behaviour; concurrent vamps cannot both consume one GO.
  • An in-file vamp plays the intro once, repeats only Loop In–Loop Out, and continues through the outro after release.
  • Audio loop-boundary QA measures the discontinuity and includes an audible test; “seamless” is accepted only if no restart gap is heard.
  • Different Playlist cues can run concurrently and Stop on one does not stop unrelated playback.
  • Pause freezes media and delay timers; resume does not lose or duplicate an item.
  • Save/reopen preserves cue order, repeat settings and stable cue references.
Verification bar: gofmt, focused runner/model tests, go test ./..., go build, git diff --check, then a native Gio smoke run proving the playlist status, transport controls and output window behaviour are visible.

Decisions to lock before implementation

Recommended: references, not copies

Playlist items point at existing cue IDs. One cue edit updates every playlist that uses it. The same cue can appear more than once.

Recommended: groups stay separate

The current GroupID work is organisational. Do not make every group runnable or overload group movement rules with playlist semantics.

Recommended: suppress child links

A playlist owns its order. Only the Playlist cue’s link fires after the sequence has completely finished.

Recommended: stop on error

For live use, silent skipping is surprising. Start with Stop and surface the failed item; add opt-in Skip later.

Recommended: GO exits at a boundary

The normal release finishes the current cue, playlist vamp pass or media Loop Out. Keep immediate exit as a clearly labelled secondary action.

Recommended: explicit transport focus

One active runner owns GO. Starting a sequence focuses it; selecting another active sequence moves focus. The sidebar always names what GO will control.
