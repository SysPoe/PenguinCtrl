Executive verdict

Not ready for show-critical deployment

The application is a promising functional prototype, but its present failure semantics are unsafe for a heavy theatrical environment. A cue can be accepted by the engine while the corresponding output event is silently discarded; pause and seek do not reschedule the engine's end timer; audio is tied to an output window and uses blocking work in a real-time callback; output-window loss creates ghost playback; and many runtime errors never reach the operator. These are deterministic defects in current code paths, not merely missing enterprise polish.

Use it only in rehearsal, non-critical playback, or with an independent, instantly available fallback until the critical items in this report are fixed and fault-injection tests pass.

What is already good

  • The app is local and native; it does not depend on a browser or localhost service.
  • Show snapshots and many core structures are protected by locks, show saves attempt a temporary-file replacement, and archive extraction includes a path traversal check.
  • Playback has explicit cancellation contexts, separate preview routing, cue warnings, a focus-loss warning, an audio-device warning, and black idle output windows.
  • Targeted non-UI tests and the race detector passed during this audit. The limitation is coverage: the most failure-sensitive behaviours are not tested.

Runtime architecture and failure domains

One process owns the operator window, every output window, cue scheduling, show mutation, autosave/transcoding, FFmpeg child processes, audio devices, and remote-control transmission. A failure or resource stall in any of these paths can therefore affect all show functions.

Critical findings — fix before show-critical use

R-01 CriticalPlayback and control events are silently dropped

Impact: a GO, STOP, fade, seek, blackout, or remove can exist in engine state but never reach the output window. The operator may see a cue as active while nothing plays, or press STOP while output continues.

Evidence: playback/events.go:105-113 uses a non-blocking send with an empty default; subscriber buffers are only 32 events. media/manager.go:181-198 adds another bounded handoff. There is no sequence number, acknowledgment, retry, or reconciliation after a dropped incremental event.

Recommendation: replace the lossy fan-out with a per-output state machine and reliable command mailbox. Give every mutation a monotonic sequence number; require the output to acknowledge application; on a gap, send a complete authoritative snapshot. STOP/blackout must use a reserved, non-droppable priority path. Add queue-depth, gap, and apply-latency telemetry. Test with a deliberately frozen output event loop.

R-02 CriticalPause and seek do not correct lifecycle timers

Impact: paused media still reaches its originally scheduled logical end; seeking backward can end early and seeking forward can end late. End links may fire while media is paused or at the wrong point in the file.

Evidence: playback/engine.go:566-600 schedules one wall-time end goroutine and sets EndScheduled. playback/engine.go:632-667 updates position/paused flags but neither cancels nor recreates that timer. The player restarts on seek/resume in media/player.go:276-325, while engine timing remains unchanged.

Recommendation: give each instance a lifecycle generation/cancel function. Pause cancels its fade/end timers; resume and seek materialise position and schedule fresh timers from remaining media time. Ignore reports from stale generations. Use one injectable monotonic clock and build deterministic tests for pause-before-fade, long pause, forward/back seek, repeated seek, and Stop All races.

R-03 CriticalAudio performs blocking I/O in the real-time callback and opens a device per player

Impact: FFmpeg scheduling, pipe stalls, garbage collection, or a slow disk can block the hardware callback and cause clicks, dropouts, or device hangs. Concurrent cues can exhaust or contend for Windows audio endpoints. Audio also disappears when its owning output window closes.

Evidence: media/audio.go:116-127 calls io.ReadFull directly inside the malgo data callback. media/audio.go:61-105 initialises and starts a new device for every player. Players are stored and closed by outputWindow in media/manager.go:148-209.

Recommendation: build one long-lived mixer per physical device. Decode into bounded lock-free or carefully synchronised ring buffers on worker goroutines; the real-time callback must only copy ready samples, apply precomputed gain, and zero-fill on underrun. Keep audio independent of visual windows. Expose underrun counts, callback timing, buffer occupancy, sample clock, and endpoint state.

R-04 CriticalAudio unplug/replug has detection but no continuity or recovery policy

Impact: unplugging a selected endpoint makes new cues fail; an already-open device has no reconnection path. Video can continue silently because its audio-start error is intentionally ignored. Replugging does not rebind active streams.

Evidence: media/manager.go:50-98 creates a warning by polling enumeration. media/audio.go:75-90 rejects a missing selected ID. media/player.go:163-167 returns audio startup errors only for audio-only media, discarding them for video. There is no device notification, mixer restart, fallback, or recovery state.

Recommendation: use Windows endpoint notifications where available, with a short polling fallback. Define explicit per-route policy: fail closed, switch to named backup, or follow system default. On loss, immediately show a latched red alarm and audible/operator alert, freeze unsafe GO actions if configured, reopen the mixer with bounded exponential retry, and either resume from the shared media clock or require a confirmed operator action. Never hide video-audio failure.

Completed sub-action: endpoint loss and video-audio startup failures now produce a latched, persistent operator alarm and preflight blocker. Continuity/rebind policy remains open.

R-05 CriticalOutput-window loss creates ghost playback and is not self-healing

Impact: Windows, a monitor hotplug, the operator, or a Gio error can close an output. Its players stop, but the engine retains live instances; waits and control cues then reason about media that is not actually playing. The output is removed and normally remains absent.

Evidence: media/manager.go:169-209 closes players with report=false on DestroyEvent and removes the window. Reopen occurs only when the explicit reopening flag is set. SyncOutputs is event-driven, not a health supervisor.

Recommendation: distinguish intentional operator close from crash/device/display loss. In show mode, prevent accidental close or immediately recreate the assigned output with backoff. On loss, reconcile every player with engine state: either resume at current monotonic position or atomically mark instances failed/stopped and block dependent links. Add heartbeat and generation IDs so stale windows cannot report against replacements.

Completed sub-action: missing displays/output windows and output/player failures are visible in preflight, the warning surface, cue rows, and the operator incident log. Automatic recovery remains open.

R-06 CompleteFailures are visible and attributable

Impact: remote cues, media control, output startup, and playback errors can fail without a persistent operator alarm. A UDP write can succeed when no console is listening. The operator cannot reliably distinguish “command accepted” from “effect confirmed.”

Evidence: playback/engine.go:1057-1070 stores only the last error; no UI reads LastError. Output event handling at media/manager.go:297-321 has no error case. Sidebar controls discard returned errors. Player startup errors are only logged at media/manager.go:337-341.

Recommendation: add a latched incident panel with timestamp, cue number/name, output/device/target, phase, severity, acknowledgment, and recovery action. A cue row must show queued, applied, confirmed, failed, or degraded. Keep bounded error history in memory and rotating disk logs. Treat “no target matched” as an operator-visible warning for control cues. Remote health must be separate from socket-write success.

Completed 13 July 2026: the operator surface, cue-row failure state, bounded/rotating history, no-target result, direct/automatic GO policy, and sent/unconfirmed UDP semantics are implemented. Protocol-level remote acknowledgement remains tracked under R-15 rather than being misrepresented as part of UI success.

R-07 CriticalShow edits and application exit are not crash-safe

Impact: closing, crashing, starting a new show, or opening another show can lose recent work. A queued autosave is not flushed on shutdown. Save As can leave a partial user-selected file. Autosave replacement has a Windows/OneDrive-sensitive gap.

Evidence: main.go:520-559 debounces autosave in an unmanaged goroutine; main.go:574-577 closes playback and returns without draining it. New/Open paths do not require dirty confirmation. Save As writes directly through the explorer handle at main.go:453-487. Replacement at main.go:733-748 temporarily moves the old file aside and ignores several cleanup/restore errors.

Recommendation: maintain a small write-ahead edit journal independent of the portable media archive. On every mutation, append and flush a versioned record; periodically checkpoint a compact show snapshot. On startup, offer verified recovery. Track dirty state and require Save/Discard/Cancel for New, Open, and Close. Save As to a sibling temporary file, fsync, validate by reopening, then replace. Retain timestamped recovery generations rather than one fixed backup.

High-priority findings

R-08 HighCue execution order is scheduler-dependent

Each dequeued command is immediately launched as an independent goroutine (playback/engine.go:185-193). Rapid GO actions and linked/embedded cues can interleave nondeterministically, including selection changes and remote sends. Use a deterministic command sequencer with explicit concurrency only for declared parallel media work. Record command sequence, accepted time, dispatch time, and completion.

R-09 HighNo pre-roll; readiness warning action complete

GO may resolve files, probe video, start one or two FFmpeg processes, enumerate/open a device, and begin decoding. Latency therefore depends on disk cache, Defender, OneDrive, codec startup, and device state. Add a show-mode preflight and pre-roll cache: validate every source, probe streams, warm decoders or buffers for imminent cues, pre-open mixers, and display a per-cue READY/NOT READY state. GO should never discover basic configuration for the first time.

Completed sub-action: asynchronous media readiness checks, per-cue state, show-wide preflight, and blocker enforcement. Decoder warming/pre-roll remains open.

R-10 HighFFmpeg supervision remains open; diagnostic action complete

exec.Command is used for playback, probing, waveform extraction, and transcoding without CommandContext or a watchdog. Playback stderr is discarded, and any decoder exit can be interpreted as a normal end (media/player.go:181-221, 235-260). Use process contexts, bounded startup/probe timeouts, captured ring-buffer stderr, explicit exit classification, and a Windows Job Object so all children terminate with the app. Surface decoder failures distinctly from EOF.

Completed sub-action: probe/player process diagnostics and stderr-derived failures are surfaced distinctly and persistently to the operator.

R-11 HighAudio and video use independent clocks and decoders

A video cue starts separate FFmpeg processes for raw video and PCM audio. Startup is sequential and there is no shared presentation timestamp, drift measurement, or correction. Long clips and pauses/seeks can visibly drift. Use a single demux/decode pipeline or a shared master media clock, timestamp frames/samples, make audio the normal clock master, drop/repeat video frames within policy, and test lip-sync over hours.

R-12 HighMedia resources are unbounded and allocation-heavy

Video dimensions are trusted, width*height*4 bytes are allocated for a buffer, and a new RGBA image plus copy is created for every frame (media/player.go:198-215). Every active video decodes even when another is the only visible player. Add dimension/frame-rate/bitrate limits, bounded frame pools, decoder concurrency and memory budgets, backpressure, and admission control. Decode only what can be presented and fail preflight rather than OOM during a show.

R-13 HighAutosave performs heavy full-archive work during playback

Every autosave calls project.Save, which walks cue media and writes an entire ZIP. Cached transcoding reduces codec cost but not hashing/copying/archive I/O. This can compete with media playback for disk, CPU, memory, and OneDrive locks. Keep fast journal/checkpoint autosave separate from explicit portable “Package Show.” Throttle background maintenance, pause it in show mode, and monitor disk latency.

R-14 HighSettings persistence is not safely transactional on Windows

config.Store.Update assigns the in-memory settings before disk save, so a save failure leaves memory and disk disagreeing. saveLocked renames settings.json.tmp directly over the destination (config/settings.go:91-121), which is not a reliable replace operation on Windows when the destination exists. Save a candidate first, flush and validate it, use a Windows-safe replace/backup sequence, and commit the in-memory value only after success. Recover orphaned temp/backup files on startup.

R-15 HighRemote delivery assurance remains open; result wording complete

UDP sockets are created per target per cue and a successful write is treated as success (remote/dispatcher.go:25-70). There is no acknowledgment, retry, heartbeat, deadline, deduplication ID, or primary/backup policy; targets are contacted sequentially. Where the console permits it, use an acknowledged protocol and idempotent command IDs. Otherwise show “sent/unconfirmed,” continuously monitor target reachability, set tight per-target deadlines, and execute redundant targets concurrently with a declared success policy.

Completed sub-action: UDP success is now reported as sent/unconfirmed and transport/target incompatibility is blocked before queueing. Active health, retry, and acknowledgement remain open.

R-16 HighNo process supervisor, panic containment, or automatic recovery

log.Fatal and os.Exit in main.go:50-97 bypass deferred cleanup. A panic in any goroutine can terminate the entire process. Use one controlled shutdown coordinator, top-level panic logging, crash dumps, and a small external supervisor/service that can restart the app into a safe black/silent recovery screen. Never auto-resume sound or remote cues after crash without an explicit, tested policy.

R-17 HighWindows display assignment and kiosk behaviour are not durable

Outputs are titled by ID and created at a default size; there is no persisted monitor identity, geometry, refresh-rate check, DPI policy, always-on-top/kiosk lock, cursor policy, or response to monitor topology changes. Persist monitor hardware identity plus a fallback rule, continuously verify placement/fullscreen, detect disconnect/reconnect, and provide a pre-show output map/test pattern with operator confirmation.

R-18 HighSleep, resume, updates, and clock discontinuity are unmanaged

Timers will react to a suspended or heavily stalled machine according to elapsed wall/monotonic time, potentially firing many cues immediately after resume. The app does not request system/display awake state or detect resume. In show mode, use Windows power requests, detect suspend/resume and large scheduler gaps, latch playback into a safe state, cancel or recompute timers, and require operator confirmation before continuing. Configure update/restart and USB power policies operationally.

R-19 HighCore cue preflight complete; full integrity gate remains open

Cue warnings are advisory and playback is still allowed. There is no single check for decodability, duration, duplicate IDs, target existence, device routes, output displays, remote health, FFmpeg capabilities, free disk, cache writability, or timing conflicts. Implement a signed/precomputed preflight result tied to a show digest; block show mode on critical errors and require an auditable override for warnings.

Completed sub-action: cue/media/device/output/transport/timing Problems preflight, GO blocker enforcement, and auditable per-show caution acknowledgement. Digest signing, disk/cache forecasting, and active remote health remain open.

R-20 HighArchive loading does not verify the promised asset integrity

The manifest stores SHA-256 and size, but extraction does not verify either (project/archive.go:185-215). It also lacks explicit archive entry/total size limits and completeness/duplicate checks. Verify CRC, declared size, SHA-256, kind/format, and that every referenced asset exists before replacing the current show. Extract to a temporary directory and atomically publish the fully validated cache. Cap entry count, expansion ratio, and total bytes.

R-21 HighUnsafe pointer-return APIs undermine locking guarantees

ShowManager.GetCue, GetCueByID, SelectedCue, and Cues return pointers to internal state after releasing the lock (show/manager.go:192-214, 268-275). Even if current UI usage is limited, future/background callers can race with slice mutation or mutate without change notification/autosave. Remove these APIs or return deep copies; expose mutation methods that hold the lock and always emit a versioned change event.

R-22 HighSynchronous device checks remain; cue-warning file probes complete

Cue warnings call os.Stat, and the main cue table calculates warnings while laying out cues. Audio enumeration is also initiated from the frame path once per second. A missing network/OneDrive path or wedged device API can freeze keyboard and GO handling. Move all filesystem/device probes to cancellable workers, cache versioned results, impose deadlines where possible, and keep the UI event loop free of blocking I/O.

Completed sub-action: cue media filesystem/decode probes now run asynchronously and cache state/errors outside the Gio layout loop.

R-23 HighCache growth and disk exhaustion are unmanaged

Extracted shows and transcoded assets are retained under the user cache with no quota, free-space check, eviction, or cleanup. Disk-full failure can therefore occur during save or immediately before a performance. Add content-addressed reference tracking, configurable quota, least-recently-used cleanup outside show mode, reserved free-space thresholds, and a preflight forecast for packaging.

R-24 HighAutomated coverage misses almost every fault boundary

The measured tree had 12 test functions across five files. Passing tests and race checks do not exercise output event loss, player timers, decoder failure, archive corruption, settings replacement, rapid command order, window close, or device unplug. Adopt the programme in this report, add CI on the exact supported Windows versions, and require fault-injection/soak evidence for release candidates.

Medium-priority hardening

R-25 MediumLogging is not operationally usable

Most diagnostics go to the default logger or are discarded. A GUI launch may leave no accessible console. Add structured rotating logs with session/build/show IDs, high-resolution timestamps, cue and event sequence IDs, device/display changes, FFmpeg exit summaries, queue depth, underruns, save/recovery events, and operator actions. Provide a one-click support bundle with bounded logs and configuration redaction.

R-26 MediumBackground work lacks lifecycle ownership

Waveform extraction, duration probing, autosave, transitions, fades, and UI callbacks create goroutines without a common task group. Some can block sending to the bounded uiActions channel after window shutdown. Introduce application-scoped contexts, an errgroup-style owner, bounded worker pools, and shutdown deadlines. No goroutine should outlive its document/output/session generation.

R-27 MediumMultiple visible video instances do not form a defined compositing model

The newest-started video/image is selected and older players keep decoding. Crossfade/layer behaviour is therefore not an explicit stable contract. Define output layers, z-order, transition rules, and whether opacity and audio gain are coupled. Stop or suspend obscured decoders when safe; test same-timestamp starts and overlapping fades.

R-28 MediumGain semantics can silently differ from cue values

dbVolume caps linear gain at 1.0 (media/player.go:542-547), so positive dB settings do not boost even though state can report them. Validate/limit UI values to the implemented range or implement headroom, mixing, metering, clipping protection, and a limiter. Never silently reinterpret an entered show level.

R-29 MediumWindow/UI ergonomics can hinder emergency control

The operator window has a fixed 1300×720 minimum, which can be problematic under Windows DPI or emergency fallback displays. Output fullscreen toggles on double-click, which is easy to trigger accidentally. Support responsive layouts, persist placement, provide a deliberate lockable fullscreen control, and keep STOP/BLACKOUT reachable at every scale and focus state.

R-30 MediumNo release engineering evidence

No CI workflow, packaging script, Windows manifest/resource, version injection, artifact signing, SBOM, reproducible-build procedure, or operator-facing release notes were present. Pin and scan dependencies, build on clean Windows workers, sign artifacts, publish hashes/SBOM, embed commit/build/config schema versions, and exercise install/upgrade/rollback.

R-31 MediumShow format evolution is brittle

The archive format is version 1 with a strict equality check and no migration/compatibility tests. Add explicit JSON field names and defaults, schema validation, forward-compatible unknown-field policy, migration fixtures for every released version, and golden files. Never make the only copy of a show the migration target.

R-32 MediumHealth state is polling/text-based rather than actionable

Audio warnings are useful but do not include selected endpoint identity, affected active cues, last successful callback, or recovery progress. Create a unified health model for engine, outputs, devices, decoders, disk, archive, and remote targets with Normal/Degraded/Failed/Recovering states and clear operator actions.

R-33 MediumNo external timecode or deterministic timeline strategy

For complex theatre integration, independent local timers are insufficient for synchronising departments and recovering from jumps. If the product scope includes timed sequences, define support for a master monotonic timeline and optional LTC/MTC/OSC timecode, including chase, discontinuity, hold, and resync policies. Keep manual cue stacks independent where external timecode is inappropriate.

R-34 MediumNo redundancy or rehearsed fallback handoff

The app is a single control and playback node. For heavy productions, specify a warm spare with prevalidated identical show/media, audio/display mappings, and a safe manual or heartbeat-gated takeover method. Do not allow both nodes to issue remote GO simultaneously. Rehearse transfer, split-brain prevention, and return-to-primary.

Recommended target architecture

  1. Deterministic show coordinator: one ordered command log, one injectable monotonic clock, explicit state transitions, generation IDs, and a priority emergency-control lane.
  2. Reliable output agents: each output applies sequenced desired state, acknowledges it, detects gaps, and can be restarted/reconciled independently. A separate process is preferable for fault isolation.
  3. Central audio engine: one mixer per endpoint, pre-opened devices, decoder workers feeding bounded ring buffers, meters/underrun telemetry, and policy-driven endpoint failover.
  4. Timestamped media pipeline: shared demux/clock for audio and video, pooled buffers, bounded decode resources, preload, and explicit end/error distinction.
  5. Durable document service: write-ahead edit journal plus small checkpoints; portable archive packaging is an explicit background/export operation, not routine autosave.
  6. Health and incident service: a unified state model, structured rotating logs, operator alarms, build/show/session IDs, and support bundle export.
  7. External supervisor: owns process restart and crash collection and always restarts outputs black/silent. A warm spare handles machine-level failure.

Reliability test programme

Deterministic automated tests

  • Fake clock tests for pre-wait, post-wait, pause/resume, seeks, fade overlap, Stop All, timecode markers, link suppression on failure, and suspend-sized clock jumps.
  • Reliable bus tests with slow/dead subscribers, queue saturation, sequence gaps, output restart, duplicate/stale acknowledgment, and priority STOP/blackout.
  • Settings tests for Windows replacement failure, disk full, read-only directory, corrupt JSON, orphan temp/backup recovery, and in-memory rollback.
  • Archive tests for truncation, missing/duplicate assets, wrong checksum/size, zip bomb limits, unsafe paths, interrupted extraction, old-version migration, and round-trip golden files.
  • Decoder tests for missing FFmpeg, startup timeout, corrupt streams, early exit, huge dimensions, no audio stream, no video stream, variable frame rate, and stale process reports.
  • Remote tests for deadline, target isolation, protocol payloads, retry/deduplication policy, unavailable DNS, and partial multi-target success.

Suggested measurable budgets

  • Zero lost control events and zero unacknowledged state gaps in a 24-hour stress run.
  • STOP/blackout dispatch p99 under 20 ms inside the application at supported maximum load.
  • Preloaded audio onset p99 under an agreed production threshold (typically 20–50 ms), measured at physical output.
  • No real-time audio callback blocking, allocations, or locks; zero underruns in the supported load matrix.
  • A/V sync remains within the agreed threshold (for example ±20 ms) for the longest supported clip.
  • Output/device-loss alarm within one second; recovery or declared failure within a bounded, documented time.
  • Crash recovery loses no acknowledged edit and never auto-fires a cue.

Windows and show-day hardening

Operational controls cannot repair software defects, but they reduce environmental variance after the critical code work is complete.

Machine build

  • Use a dedicated, tested Windows image and local administrator-controlled update window; disable automatic restart during performances.
  • Use High/Ultimate Performance power settings; disable sleep, hibernate, USB selective suspend, display sleep, and NIC power saving while in show mode.
  • Keep show and cache files on a local SSD. Package/synchronise through OneDrive outside show mode; do not play directly from a cloud placeholder.
  • Pin and document GPU, audio-interface, chipset, and network driver versions. Disable enhancements/spatial audio and select a fixed supported sample rate.
  • Exclude the signed application and local media/cache directories from real-time scanning only under the organisation's approved security process; validate the exact configuration.
  • Disable notifications, Focus Assist interruptions, screen savers, hotkeys/overlays, and unrelated startup/background applications.
  • Use cabled network for remote control, a dedicated switch/VLAN where appropriate, static addressing, and UPS power for the PC, displays, interface, and network.

Pre-show checklist

  1. Boot from cold; verify app/build hash and open the local packaged show copy.
  2. Run full preflight: archive hashes, media decode, device routes, sample rate, displays, remote targets, disk space, cache, and clock.
  3. Show test pattern/identify on every physical output and require operator confirmation of mapping/fullscreen.
  4. Play a test tone through every playback and preview route; verify silence/mute/level behaviour and backup route.
  5. Exercise GO, pause, seek, fade, STOP ALL, blackout, remote cue, and the first/last critical cue.
  6. Verify supervisor, logs, crash-recovery checkpoint, warm-spare show/hash, and takeover interlock.
  7. Enter locked show mode; suspend packaging, indexing, updates, sync, and nonessential maintenance.

Fallback plan

Keep an independent fallback that does not share the primary machine, audio interface, display adapter, or power point where practical. Define who calls the failure, who stops/blackouts, who transfers audio/video/remote control, and how split-brain is prevented. Rehearse this with the actual operators.

Prioritised delivery roadmap

Phase 0 — Restore a trustworthy baseline

  • Land or isolate current work; require clean full test/build/vet.
  • Add Windows CI and versioned signed artifacts.
  • Capture structured logs and a visible incident surface.
  • Freeze a release test show and hardware matrix.

Phase 1 — Correct unsafe semantics

  • Reliable sequenced events and priority STOP.
  • Generation-based timer pause/seek correction.
  • Output-loss reconciliation and recovery.
  • Durable edit journal and safe save/close flow.
  • Propagate every playback/audio/remote error.

Phase 2 — Rebuild media reliability

  • Central audio mixer and ring buffers.
  • Shared timestamped A/V clock.
  • Preload/readiness, resource bounds, FFmpeg supervision.
  • Device/display notification and failover policy.
  • Move packaging away from autosave.

Phase 3 — Prove production readiness

  • Fault-injection and 24-hour soak suites.
  • Windows show-mode controls and preflight.
  • Supervisor/crash recovery and warm spare.
  • Operator runbook, training, incident drills.
  • Measured latency, sync, recovery, and capacity limits.

Release acceptance gates

A release should not be labelled theatre-ready until all of the following are evidenced on the supported Windows/hardware matrix:

  1. Clean checkout: full tests, race tests, vet/static analysis, formatting, dependency/vulnerability scan, and signed build all pass in CI.
  2. No silent drops: every command is sequenced, applied/failed, acknowledged, and recoverable after output restart.
  3. Pause, resume, seek, fade, end, links, Stop All, and timecode pass deterministic fake-clock tests and real-media tests.
  4. Audio callback meets real-time rules; supported cue/output load produces zero underruns for the soak duration.
  5. Unplug/replug of every supported audio route and display follows the documented, tested policy with a visible incident.
  6. Decoder failure, corrupt media, missing media, remote outage, disk full, file lock, sleep/resume, and process crash all fail safely.
  7. Every acknowledged edit survives crash/power interruption; every archive is verified before replacing the live document.
  8. Preflight validates the exact show/hardware state and blocks critical defects; overrides are explicit and logged.
  9. Capacity limits (cues, outputs, resolution, concurrent streams, markers, runtime) are measured, documented, and enforced.
  10. A warm-spare handoff and operator incident drill succeed using the actual production system.
Recommended immediate focus: R-01 event delivery, R-02 timer correctness, R-03/R-04 audio architecture and recovery, R-05 output reconciliation, R-06 operator-visible failures, and R-07 durable show state. These changes remove the largest “looks active but is not actually safe” failure modes.
